目标通知安排编程、短期项目或类似考核时，训练应同时覆盖 **理解任务、独立实现、解释错误、确认提交物**。不要只统计刷题数量，也不要把本机运行成功当成已经满足考核环境。

以下是练习建议，允许使用的语言、库、网络、AI 工具和团队协作方式，均以具体考核规则为准。

## 先跑通一次完整提交

正式训练前，先核对并试用目标允许的环境。完整程序与指定函数的评测形式不同，不能把自己熟悉的输入输出方式直接套过去。

| 核对事项 | 要确认什么 |
| --- | --- |
| 提交物 | 完整程序、函数、文件还是项目目录 |
| 环境 | 语言与编译器版本，允许的依赖、编辑器和工具 |
| 数据 | 输入范围、结束方式、输出格式及数值要求 |
| 资源 | 时间、内存和其他运行限制 |
| 流程 | 测试、提交、反馈及重新提交怎样处理 |

用一份最小程序练习从编写到提交的完整过程。环境问题单独记录，不把排查编译器或目录结构的时间误计成算法能力不足。

## 每道题留下三样东西 {#practice-record}

1. **题意摘要。** 写清输入、输出、范围与需要满足的条件，先举一个自己能手算的例子。
2. **方案说明。** 解释选择依据与复杂度，再独立实现；无法说明复杂度时，回到数据规模和基本操作检查。
3. **反例或错误记录。** 记录一个曾使自己判断错误的条件，以及为什么原方案不适用。

普通情况通过后，再按题目范围挑选空或最小输入、边界值、重复元素、特殊顺序等情形；只检查题目允许的输入，不把不存在的要求加进程序。不存在适用于所有题目的固定测试清单。

## 根据错误决定下一轮练什么

| 观察到的问题 | 先定位哪里 | 下一次训练任务 |
| --- | --- | --- |
| 题意理解偏差 | 条件遗漏或样例被误当全部要求 | 不写代码，先手算多个小输入并复述题意 |
| 思路正确但实现失败 | 状态更新、下标、边界或语言细节 | 把失败输入缩小，跟踪第一次产生差异的位置 |
| 运行超时或资源超限 | 输入规模、复杂度与实现中的额外工作 | 重新估算操作量，比较可行方案 |
| 输出不符 | 格式、溢出、精度或结果逻辑 | 区分结果错误和格式错误，分别构造验证 |
| 本机正常、评测失败 | 环境、依赖、输入方式或未覆盖条件 | 用规定环境重跑，检查是否依赖本机文件与状态 |

不要靠反复改几个条件碰运气。每次修改写下一句“这次要验证什么”，再看结果是否支持判断。

## 专题练习与限时模拟分开

专题练习用于补缺口，可以慢下来核对概念和实现；限时模拟用于检验选题、时间分配、调试和提交流程。两者分开记录，避免一次模拟不顺就把整门知识推倒重来。

题目选择依据目标范围和自己实际暴露的问题。枚举、排序、二分、基础数据结构、搜索、动态规划与图算法都是可能的训练专题，但不是统一必考目录。

模拟结束后只选少量最影响结果的问题复测。更换输入或做一道相近但不同的题，确认自己理解了原因，而不是记住上一题的修补代码。

## 短期项目先确定可以验收的最小版本 {#minimum-delivery}

先把要求分成“必须交付”“可补充”和“本次不做”，再为必须部分写出可观察的验收条件。先完成输入到输出的最短完整路径，再增加功能。

面向不同项目，可以这样定义最小演示：

- 嵌入式任务：能够按要求接收或采集输入、完成处理并输出结果，同时保留必要日志。
- 控制或机器人任务：在明确的测试条件下完成一个指定动作或流程，记录条件、观察与尚未验证的情况。
- 软件或视觉任务：从约定输入生成可检查的输出，说明运行步骤与评价方式。

这些只是定义交付物的方法，不表示相应考核一定采用这些任务。

## 从干净目录检查交付物

提交前，将准备交付的内容复制到单独目录，按自己写的说明从头运行一次，检查是否缺文件、依赖个人绝对路径或使用未声明的数据。

团队任务还应留下接口约定和分工，能说明自己完成的内容。展示材料至少回答：需求是什么、怎样运行、验证过什么、仍有什么限制。按规则交付必要文件，不把无关缓存、私人数据或未授权资料混入压缩包。

AI 工具即使被允许，也不能代替本人解释和验证。生成的实现仍需按同样标准检查；考核禁止的工具和外部协助不用于实际作答。
