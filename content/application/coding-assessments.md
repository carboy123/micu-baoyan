只有在目标通知安排机试、短期项目或类似考核时，才按对应形式准备。不同院校的提交方式、语言、工具和评价要求可能不同，不能依据他人的一次经历推定本轮安排。

## 先弄清提交形式

完整程序式评测通常需要自行处理输入输出；函数式评测通常提供调用接口。先核对目标采用哪种形式，并熟悉允许的语言、编译器、时间限制、内存限制、库函数及网络使用要求。

| 核对事项 | 需要确认的问题 |
| --- | --- |
| 提交物 | 完整程序、指定函数、文件还是项目目录 |
| 运行环境 | 允许的语言版本、编译器、依赖与编辑环境 |
| 输入输出 | 数据范围、输入结束方式、输出格式 |
| 资源限制 | 时间与内存限制，其他运行约束 |
| 可用工具 | 是否允许查资料、联网或使用特定辅助工具 |
| 现场流程 | 怎样测试、提交、查看反馈，是否有练习环境 |

环境规则不明确时，通过通知中的官方渠道确认。不把自己平时使用的开发环境默认视为考场可用环境。

## 用完整解题过程检查能力

1. 从题面提取输入范围与输出要求，先确认理解的问题是什么。
2. 写出小样例，考虑边界情况，用它们检查思路。
3. 说明算法的时间、空间复杂度，判断是否适合给定范围。
4. 在允许的语言和环境中独立实现输入输出、调试与提交。
5. 根据反馈分析边界、溢出、超时、格式等原因，不只盯着样例是否通过。
6. 在限定时间内调整题目顺序，考后保留错误与修订记录。

这些动作比单纯记录“今天做了几题”更能帮助定位薄弱环节。训练题的通过结果与真实考核表现也不应混为一谈。

## 怎样选择练习专题

按目标范围和自身薄弱项选择枚举、排序、二分、基础数据结构、搜索、动态规划或图算法等主题。基础稿所参考的江南机试材料还列举 DFS、BFS、最短路、最小生成树等线索，可按需要加入计划。

这些名称不构成统一必考清单，也不存在做完固定题单就一定通过的保证。对每个选定专题，至少检查能否说明思路、解释适用条件、实现并识别常见错误。[相关基础自检]({{< relref "application/review-basics.md" >}})

## 做一次接近目标环境的限时模拟

采用相同的提交形式、接近的时长和明确的可用工具。模拟结束后，同时复盘解题思路和操作过程：是否把大量时间消耗在输入格式、环境配置或反复调试同一个错误；是否因为没有检查边界而误判方案；是否需要调整做题顺序。

可以保留这样一条记录：题目或专题、原思路、失败现象、真正原因、修正方案、下次复测。复盘后再做一次相关练习，确认自己掌握了原因，而不只是记住答案。

## 短期项目、团队任务与 AI 工具

若通知安排短期项目或黑客松等形式，先明确需求、提交物、数据来源、允许工具和个人贡献记录方式。可练习先做出最小可运行方案，再验证、完善并准备展示；是否采用团队形式和怎样评价，仍按项目规则。

团队任务要能区分共同成果和个人工作，并说明接口、分工与验证。展示时讲清需求如何理解、做了什么、怎样确认结果、尚有哪些限制，不仅展示最终界面。

AI 工具是否允许、可使用到什么程度，以具体规则为准。即使允许生成代码，提交者仍需要能够解释、运行和验证；不将工具生成的结果直接当作已经确认正确的实现。
